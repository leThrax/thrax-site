# CLAUDE.md

## Project state

This started as the default `npm create vite` react-ts scaffold, grew into a single-page filterable showcase of the site owner's software stack, and is now a multi-page personal portfolio built around that same showcase — see "Site structure" for the page/routing overview and "Software-stack showcase" for the original page's architecture, still intact as one of the pages.

## Site structure

Six public pages, client-side-routed with `react-router-dom` (`src/main.tsx`), plus the separate `/admin` control panel:

| Route | Page | Purpose |
|---|---|---|
| `/` | `HomePage` | `WhoamiHeader` (neofetch-style intro) + quick-link cards to the other five pages |
| `/software` | `SoftwareStackPage` | The original software-stack showcase — see "Software-stack showcase" below |
| `/cv` | `CvPage` | Static hand-authored CV (experience/education/skills) |
| `/projects` | `ProjectsPage` | Public GitHub repos, fetched live from the GitHub REST API |
| `/blog`, `/blog/:slug` | `BlogIndexPage`, `BlogPostPage` | Markdown tutorials/reviews, admin-authored, stored in Supabase |
| `/hardware` | `HardwarePage` | PC/homeserver/laptop specs with a switchable, rotatable real 3D model (Sketchfab, admin-uploaded) — see "Hardware page" below |
| `*` | `NotFoundPage` | Catch-all 404, nested last under the `SiteLayout` route so it still gets nav/boot chrome |
| `/admin` | `AdminPage` | Unchanged control panel, kept outside the public layout |

All five public-page routes plus `/`, `/software`, `/cv`, `/projects`, `/blog`, `/blog/:slug`, and `/hardware` are nested under a shared `<Route element={<SiteLayout/>}>` in `main.tsx`; `/admin` is registered as its own sibling top-level route, not wrapped in `SiteLayout` (no public nav or boot sequence there — it stays a distinct control-panel surface).

`src/layouts/SiteLayout.tsx` owns what used to live directly in `App.tsx` back when the software-stack page was the site's only public route: the `MotionConfig`/`AnimatePresence` boot-sequence gate (`BootSequence`, still session-gated, still bypassed under `prefers-reduced-motion`) and the outer page-load `containerVariants`/`sectionVariants` fade-in wrapper (now shared, in `src/lib/motionVariants.ts`, rather than local to one page — Framer Motion propagates variants through React context, not DOM parentage, so a page's own `motion.div` sections still stagger correctly even though they render inside `SiteLayout`'s `<Outlet/>` rather than as its direct children). It also renders `src/components/SiteNav.tsx`, a persistent shell-flag-styled nav bar (`--software`, `--cv`, `--projects`, `--blog`, `--hardware`, plus a `~` home link) using `NavLink` for active-route highlighting — shared across every public page via `src/data/navLinks.ts`, which both `SiteNav` and `HomePage`'s quick-link cards read from.

`src/components/WhoamiHeader.tsx` is `HomePage`'s hero: the same bordered "terminal window" chrome as `FetchHeader` (window-dot header bar, `visitor@thrax-site` line), but showing static site/owner info instead of filter state — kept as a separate component rather than overloading `FetchHeader`, which stays specific to the software-stack page's filter flags. That chrome itself now lives in `src/components/TerminalWindow.tsx` (border, window dots, `visitor@thrax-site` prompt, dashed separator), a pure-presentational component taking the info-row `<p>` children as its only prop — every public page's header (`WhoamiHeader`, `FetchHeader`, and `CvHeader`/`ProjectsHeader`/`BlogHeader`/`BlogPostHeader`/`HardwareHeader`) wraps it, each owning only its own page-specific content rows and `useTypewriter` call rather than re-duplicating the panel markup.

**404 page**: `src/pages/NotFoundPage.tsx` renders a fake shell "command not found" error using the actual attempted path (`useLocation().pathname`) plus a `← back home` link, styled in the same terminal-error voice as `BlogPostPage.tsx`'s not-found state. Registered as `<Route path="*" .../>`, last child inside the `SiteLayout`-wrapped route group — nesting it there (rather than as a top-level sibling like `/admin`) means an invalid sub-path like `/admin/foo` still falls through to it correctly, since `/admin` itself is matched as an exact path, not a prefix.

**Per-route document titles**: `src/hooks/useDocumentTitle.ts` is a one-line `useEffect(() => { document.title = title }, [title])` hook, called once near the top of every page component with a literal (or, for `BlogPostPage`, dynamic-once-`post`-loads) title string — the same "synchronize with an external system" justification already used for `Icon.tsx`'s lazy-SVG-load effect. `index.html`'s static `<title>` is now just the pre-hydration-flash value. `index.html` also carries generic, sitewide (not per-page) `og:title`/`og:description`/`og:type`/`twitter:card` meta tags — true per-page social-preview content isn't possible without server rendering, which this static SPA deliberately doesn't have, so these are deliberately the same for every URL.

**Command palette**: `src/components/CommandPalette.tsx`, a controlled component (`open`/`onClose` props) mounted by `SiteLayout.tsx` as an always-present sibling inside `MotionConfig` (live from first paint, not gated behind the boot sequence). `SiteLayout` owns the `paletteOpen` state and the global Cmd+K/Ctrl+K `window.addEventListener('keydown', ...)` toggle listener (same effect shape as `ItemDetail`'s Escape handler), and passes `onOpenPalette` down to `SiteNav.tsx`'s small `⌘K` discoverability badge — plain prop-passing rather than a new context/event-bus pattern, consistent with how the rest of the codebase wires cross-component state. Destinations are `[{ path: '/', label: 'Home' }, ...NAV_LINKS]` (so `/admin` is excluded by construction, matching `SiteNav`/`HomePage`'s existing quick-links); matching is a plain trim+lowercase+`.includes()` filter, the same minimal philosophy as `lib/filtering.ts`'s `matchesSearch` rather than a fuzzy-match library. The modal/backdrop structure mirrors `ItemDetail.tsx` (no `layoutId` — nothing to morph from), with its own internal `AnimatePresence` since it's always-mounted rather than conditionally rendered by a parent.

**CV page**: content lives in `src/data/cv.ts` (a typed `CvData` object — name/title/summary/links/skills), hand-edited like any other source file; currently placeholder content (`TODO` strings) — replace with real details. Not admin-editable; this static content changes rarely enough that a Supabase table/admin form would be overhead without benefit. Experience/education instead live in an admin-managed, drag-and-drop-reorderable **timeline** (`timeline_entries` table — see "Supabase layer"): `src/types/timeline.ts`'s `TimelineEntry` (`role`, `org`, `startDate`, optional `endDate`/`description`, an admin-controlled `position`), `src/lib/timeline.ts` (CRUD mirroring `lib/devices.ts`, plus a `reorderTimelineEntries(orderedIds)` bulk-position-update with no precedent elsewhere in the codebase), `src/hooks/useTimelineEntries.ts`. Admin CRUD (`src/admin/TimelineEntryForm.tsx`/`TimelineEntryList.tsx`, a "Timeline" tab in `AdminPage`) adds real drag-and-drop via `@dnd-kit` — the only drag-reorderable list in the app — with a grip-handle-only drag target so Edit/Delete stay independently clickable; `TimelineEntryList` keeps local `displayOrder` state reconciled from the `entries` prop, the one place in the codebase that optimistically reorders ahead of the server round-trip (drag needs instant feedback; the parent still persists via `reorderTimelineEntries` then refetches for correctness). Public rendering is `src/components/TimelinePath.tsx`: a vertical accent-line "path" with a glowing solid dot for the ongoing role (`endDate` unset) and a smaller hollow-ring dot for past ones, dates formatted via `src/lib/formatDateRange.ts` ("Present" when `endDate` is unset), multi-line `description`s rendering as a bullet list and single-line ones as a paragraph.

**Projects page**: `src/lib/github.ts`'s `fetchGithubRepos(username)` hits the public, unauthenticated GitHub REST API (`api.github.com/users/{username}/repos`), filtering out forks/archived repos, sorted by most-recently-updated. `src/hooks/useGithubRepos.ts` mirrors the `useItems`-shaped fetch/loading/error/refetch hook pattern. The username comes from `VITE_GITHUB_USERNAME` (see "Env vars" below).

**Pinned (contributed) repos**: repos the owner contributed to but doesn't personally own never show up in the per-username list above, so `ProjectsPage.tsx` additionally reads a small admin-managed `pinned_repos` table (just `"owner/repo"` strings — see "Supabase layer") via `usePinnedRepos()`, then live-fetches each one's real data with `fetchGithubRepo(owner, repo)` (same GitHub API, single-repo endpoint) and tags it `contributor: true` on the shared `GithubRepo` type. The two lists are merged (de-duplicated by GitHub's numeric repo `id`, in case a pinned repo is somehow also owned) and sorted together by `updatedAt`; `ProjectCard` shows a small "contributor" label when `contributor` is set. A pinned repo that 404s (renamed/deleted/made private since being pinned) is silently dropped from the public grid rather than breaking the page — `src/lib/github.ts`'s `parseRepoRef(input)` accepts either a full GitHub URL or a bare `owner/repo` string, used both when the admin adds one and to build the fetch. Admin management is `src/admin/PinnedRepoList.tsx` (a third "Projects" tab in `AdminPage`, alongside Items/Posts): pasting a ref calls `fetchGithubRepo` to verify the repo actually exists/is public *before* persisting it, the same "verify against the external system first" pattern as the Wikipedia auto-fill.

**Blog**: posts are Supabase-backed (`posts` table — see "Supabase layer") with a markdown `body`, authored through a new admin form (`PostForm`/`PostList`, a second managed collection in `AdminPage` alongside items, switched via a simple Items/Posts tab). `published_at` being null means "draft" — RLS lets the admin see/edit drafts but the public `select` policy only returns rows where `published_at is not null`; `BlogIndexPage` additionally filters client-side to published posts as a defense-in-depth measure since `usePosts()` is shared with the admin's draft-inclusive list. `BlogPostPage` fetches a single post by slug (`fetchPostBySlug`, via `useParams().slug`) and renders `body` with `react-markdown` + `remark-gfm` inside a `font-sans` (Inter) container — same mono-headings/humanist-body-prose convention `ItemDetail` already uses for description text — styled via scoped Tailwind arbitrary-value selectors (`[&_h2]:...`, `[&_pre]:...`) rather than the `@tailwindcss/typography` plugin, to avoid adding a dependency for a single page. Fenced code blocks are syntax-highlighted via the `rehype-highlight` plugin (auto-detects language, bundles `lowlight`'s "common" language subset rather than all ~190 — a modest bundle-weight addition, same spirit as the hardware page's three.js note below); its `hljs-*` token classes are colored via a small hand-rolled theme in `src/index.css` using only the site's existing `--color-*` tokens rather than a canned highlight.js stylesheet, the same reasoning as skipping `@tailwindcss/typography`.

**Blog images/video**: `PostForm.tsx` has "Image"/"Video" file inputs below the body textarea; picking a file uploads it via `uploadPostMedia(id, file)` (`src/lib/storage.ts`, a copy of the existing `uploadIcon` targeting a separate `post-media` Storage bucket) and inserts the right snippet at the textarea's current cursor position (tracked via a `ref` + `selectionStart`/`selectionEnd`) — `![filename](url)` for images, or a raw `<video controls src="url"></video>` tag for video, since markdown has no native video syntax. `BlogPostPage.tsx` adds the `rehype-raw` plugin to `<ReactMarkdown>` so that raw `<video>` tag actually renders as an element instead of being escaped as literal text (react-markdown strips raw HTML by default without it) — safe here specifically because `posts.body` can only ever be written by the authenticated admin (RLS restricts `insert`/`update` on `posts` to the admin uid), the same "trusted, admin-only-writable content" reasoning already used for `Icon.tsx`'s `dangerouslySetInnerHTML`. Both `img` and `video` get matching `max-w-full`/`w-full` + rounded/bordered styling via the same scoped arbitrary-selector wrapper as the rest of the post body.

**Hardware page**: `/hardware` shows Supabase-backed `Device`s (a PC, a homeserver, a MacBook, etc. — `devices` table, see "Supabase layer") behind a `--{id}`-flag-styled switcher (same chip visual language as `FilterChip`); the selected device's specs render as a `❯ label: value` list beside a `DeviceScene` (`src/components/hardware/DeviceScene.tsx`) — an `@react-three/fiber` `<Canvas>` with drei's `<OrbitControls>` (drag-to-rotate, scroll-to-zoom) loading each device's own real `.glb` model (`device.modelUrl`, admin-uploaded — see "Admin panel" below) via drei's `useGLTF`, inside a `<Suspense>` boundary since GLTF loading is async unlike synchronous geometry. Loaded models are normalized on load (`GltfModel`'s `useMemo`, keyed on the loaded scene): the bounding box is computed (`THREE.Box3`) and the model is translated to center on the origin and uniformly scaled so its longest dimension is ~2.2 units — necessary because different Sketchfab uploads arrive at wildly different native scales/pivot origins, and without this every model would need per-device camera tuning against the shared fixed `OrbitControls` min/max distance. Deliberately no drei `<Environment>`/HDRI lighting preset (those fetch image assets from a CDN at runtime); lighting is a plain ambient + two directional lights, colored from the same hex values as `src/index.css`'s `--color-*` tokens (duplicated as local constants in `DeviceScene.tsx` since a WebGL canvas can't read CSS custom properties). A device with no model yet shows a "No 3D model uploaded yet." placeholder instead of an empty canvas. `.glb` uploads can be tens of MB, so `DeviceScene` doesn't fetch one automatically: it renders a "Load 3D model" button by default (local `loaded` state, initially `false`) and only mounts `<Canvas>`/`useGLTF` — and so only starts the network request — once clicked; switching devices (`key={selectedDevice.id}` in `HardwarePage`) remounts `DeviceScene` fresh, so the prompt reappears per device rather than a previously-loaded model staying resident. `OrbitControls`' idle `autoRotate` is gated behind `window.matchMedia('(prefers-reduced-motion: reduce)')`, checked once via `useMemo` — same manual pattern `BootSequence` uses, since this canvas sits outside Framer Motion's `MotionConfig` control. **Model credit**: `device.modelCredit` (`{creator, sourceUrl, license?}`, entered in the admin form alongside the upload) renders as a small link line under the viewer — `3D model by {creator} — via Sketchfab`, crediting the original author per Sketchfab's standard attribution convention. **Bundle-weight note**: `three`/`@react-three/fiber`/`@react-three/drei` are the first WebGL dependency in the codebase and unusually heavy, so — unlike every other route — `HardwarePage` is lazy-loaded (`src/components/hardware/HardwarePageLazy.tsx`, wrapped in `<Suspense>` in `main.tsx`) so the rest of the site's bundle doesn't pay for it; the `.glb` files themselves are fetched at runtime by URL (not bundled into JS), so per-model size doesn't affect the JS chunk at all. **Header**: `src/components/HardwareHeader.tsx` (the page's `TerminalWindow`-based header, see "Signature element" above) shows a device count and a `Shell:` line driven by `useTypewriter(selectedDeviceId ? `--${selectedDeviceId}` : '--none')` — since the hook's effect re-runs whenever its `target` argument changes, clicking a different device chip changes `selectedDeviceId` and automatically replays the same delete-then-retype animation `FetchHeader`'s `Shell:` line plays on filter changes, with no new animation code.

### Self-hosted deployment (Apache)

Production is self-hosted on the site owner's own server (`thrax.tyrserver.de`, DNS CNAME already pointed there), on the same Apache 2 instance that already serves other apps on that box (e.g. `vusync.tyrserver.de`, a proxied Node/Socket.IO app). Since this site is a pure static build with no backend of its own, its vhost doesn't need `mod_proxy`/`ProxyPass` the way a proxied app's does — Apache serves `dist/`'s files directly. Multiple sites share the same Apache instance and ports 80/443 via name-based virtual hosting (Apache routes by the `Host` header / TLS SNI against each vhost's `ServerName`), so this site needed no new firewall port of its own. `deploy/apache-thrax.tyrserver.de.conf` is the committed vhost (not deployed automatically — copied to the server's `/etc/apache2/sites-available/` by hand, see the file's own header comment for the full one-time setup + redeploy steps); TLS is issued/renewed via `certbot --apache`, the same pattern as the box's other vhosts, which rewrites the plain-HTTP `:80` block into a redirect-only stub and generates the `:443` block rather than that being hand-written. The vhost's own `mod_rewrite` rule (real files/dirs pass through; everything else falls through to `index.html`) is the Apache-specific equivalent of `public/_redirects`/`vercel.json` above — Apache doesn't read either of those files, they're no-ops here. It also sets `Cache-Control` (via `mod_headers`) long-lived/immutable on `/assets/` (Vite content-hashes every filename there, so a stale cache is never actually stale) and `no-cache` on `index.html` specifically (unhashed, so it must always be revalidated or a redeploy won't be picked up by returning visitors).

### Supabase setup (one-time, done by the project owner)

1. Create a project at supabase.com (free tier is sufficient).
2. In the SQL Editor, run `supabase/schema.sql` from this repo — creates the `items`, `tags`, `categories`, `posts`, `pinned_repos`, `devices`, and `timeline_entries` tables, enables RLS, adds public-read/admin-write policies, and (optionally) seeds 6 demo items + the 6 starter tags. Leave the `'<ADMIN_USER_ID>'` placeholders as-is for now. The whole file is safe to re-run any time new tables/policies are added (e.g. `posts`, added for the blog) — every `create table`/`alter table`/policy statement is idempotent.
3. In Authentication settings, disable public sign-ups, then manually create the one admin user (Authentication -> Users -> Add user).
4. Copy that user's UID and re-run the whole file with the real UID substituted in place of every `'<ADMIN_USER_ID>'` (the policies are `drop if exists`-then-`create`, so this is safe to re-run any time, e.g. after rotating the admin user).
5. Create three public Storage buckets: `icons` (custom icon uploads from the item admin form), `post-media` (image/video uploads from the blog post admin form), and `device-models` (`.glb` uploads from the hardware admin form).
6. Copy `.env.local.example` to `.env.local` and fill in the project's URL and anon key (Project Settings -> API), plus `VITE_GITHUB_USERNAME` (your GitHub username, for the `/projects` page — leaving it blank shows a config error there instead of guessing wrong).
7. Visit `/admin` locally and sign in with the admin user's email/password from step 3.

### Confirmed software-stack decisions

| Area | Decision | Why |
|---|---|---|
| Data storage | **Supabase** (hosted Postgres + Auth + Storage) | Items are added later via an admin panel, which rules out a static code-only data file |
| Icon sourcing | **`simple-icons`** npm package, looked up dynamically by slug at runtime (not a hand-maintained per-icon import map); local custom-SVG/upload fallback for anything missing | Thousands of brand SVGs (OS logos, dev tools, CLI tools), MIT licensed, no runtime network dependency. Dynamic lookup means an item added via the admin panel with a new `simple-icons` slug renders immediately, no developer/redeploy step needed |
| Styling | **Tailwind CSS v4** via `@tailwindcss/vite` | Fast to build chips/cards/responsive grid + the admin form UI consistently |
| Animation | **`motion`** (Framer Motion) | `AnimatePresence` for exit animations + `layout` prop for FLIP-based reflow when filtered items are removed |
| Filter grouping | Grouped into categories, **OR within a group, AND across groups** | Standard faceted-search semantics — selecting two OS filters shows either OS, adding a Topic filter narrows further. A flat AND-everything model would zero out results whenever two same-group chips are selected |
| Routing | **`react-router-dom`** | Reverses the original "no router" decision — that rationale (a single public route) stopped holding once the site grew to 5 public pages plus nested `/blog/:slug` post URLs; a plain `pathname` check doesn't scale to that |
| Projects data | Live **GitHub REST API** fetch, not admin-curated | New repos should appear automatically with no admin work; public repo data needs no auth |
| Blog storage | **Supabase**, markdown body, admin-authored | Same content-without-redeploy model as items/tags/categories, rather than committing post files to the repo |
| Hardware 3D models | Real **Sketchfab `.glb` models**, admin-uploaded to Supabase Storage, credited via a `modelCredit` field | Looks far better than the earlier procedural-primitive prototype; upload-not-static keeps a model swappable without a redeploy, same reasoning as icon/post-media uploads; credit info is required to respect Sketchfab creators' licensing |
| Hardware specs storage | **Supabase**, admin-editable, same CRUD shape as items/posts | Specs (RAM upgrades, etc.) are expected to change over time, unlike CV content |
| Testing | **Vitest** for pure logic, **Vitest + Testing Library (`@testing-library/react`/`user-event`) + jsdom** for components | No test runner exists yet; the filter-matching function is pure and worth locking down with unit tests. Component tests were added later for presentational components with real interaction logic (clipboard copy, controlled inputs, click handlers) rather than every component, since most pages are thin Supabase-fetch wrappers around them — see "Toolchain notes" |

### Visual design: terminal/neofetch theme

The site commits to a single fixed dark theme (no light-mode variant, no `dark:` variants anywhere) — a deliberate identity choice grounded in the content itself (Proton VPN, CachyOS, iTerm2 are exactly "ricing/dotfiles" territory), not a generic dark-mode reskin. Design tokens live in `src/index.css`'s Tailwind v4 `@theme` block:

| Token | Hex | Use |
|---|---|---|
| `--color-bg` | `#0d0f12` | page background |
| `--color-surface` | `#15181d` | cards, panels |
| `--color-surface-hover` | `#1b1f26` | card hover bg |
| `--color-border` | `#2a2f3a` | hairline borders |
| `--color-fg` | `#d8dee9` | primary text |
| `--color-muted` | `#6b7280` | dim/secondary text |
| `--color-accent` | `#7ee787` | primary accent (prompt, active/selected, links) |
| `--color-accent-2` | `#d992ff` | secondary accent (hover highlights) |

These `--color-*` names are what Tailwind v4 auto-generates `bg-*`/`text-*`/`border-*` utilities from (e.g. `bg-surface`, `text-accent`, `border-border`) — no `tailwind.config.js` needed, still CSS-first.

Type: `JetBrains Mono` as the **display/UI face** (headings, buttons, tags, card names — used almost everywhere, loaded via `<link>` in `index.html`, not a package), `Inter` as the **body face**, used only for the item description prose in `ItemDetail` where a humanist sans reads better than mono for a full sentence.

Signature element: `FetchHeader.tsx` — a bordered "terminal window" panel at the top of the public page showing live data (item count, current filter selection rendered as shell flags, e.g. `Shell: --os=macos,linux --topic=privacy`) rather than being purely decorative. The panel chrome is factored into `TerminalWindow.tsx` (see "Site structure" above) and is now the header pattern on every public page — `/` (`WhoamiHeader`), `/software` (`FetchHeader`), `/cv` (`CvHeader`), `/projects` (`ProjectsHeader`), `/blog` (`BlogHeader`), `/blog/:slug` (`BlogPostHeader`), and `/hardware` (`HardwareHeader`, whose `Shell:` line updates live on device selection the same way `FetchHeader`'s does on filter selection — see "Hardware page" above). Filter chips (`FilterChip.tsx`) are styled the same way — visually `--{tag.id}` (e.g. `--privacy`), with `aria-label` carrying the human-readable `tag.label` so screen readers still announce "Privacy," not the raw flag string.

Per-item tint: `ItemCard`/`ItemDetail` both resolve a `tintHex` — `getSimpleIconMeta(slug)?.hex` for `simple-icons` items, or `item.icon.tint` for `custom` items (see below) — and, when present, set inline `style={{ backgroundColor: 'var(--color-surface)', backgroundImage: 'linear-gradient(to bottom, ...)' }}` — a ~10%-opacity top-down wash of that color fading into `var(--color-surface)` by 60% down the card. **Important:** `backgroundColor` and `backgroundImage` are set as two separate style properties deliberately, not combined into the `background` shorthand — the shorthand resets `background-color` to `transparent` when not included in its value, and since the gradient's own colors are alpha-blended (semi-transparent at the top stop), that let the page's `body` scanline/vignette background (see below) bleed straight through the top of every tinted card. A straight top-down fade was chosen over an earlier radial/circular version specifically because it reads better against the card's sharp corners and borders. Both components apply the *same* gradient so the shared-`layoutId` morph animation between them doesn't show a jarring background snap. Inline `style` always wins over Tailwind classes regardless of specificity, which is why `ItemCard` doesn't also try to layer a `hover:bg-surface-hover` class — that would silently never apply once tinted; the `hover:border-accent` + shadow-glow hover feedback carries hover state instead, uniformly for tinted and untinted cards.

**Custom-icon tint extraction** (`src/lib/colorExtraction.ts`): custom uploads have no bundled color metadata, so a tint is extracted from the file itself, once, at upload time in `ItemForm` (same "expensive one-off work belongs in the admin flow" principle as the Wikipedia auto-fill) and stored in `items.icon_tint` — the public page never re-analyzes images. Two-tier extraction: (1) for SVGs, read the file as text and regex for `fill="#…"`/`fill:#…` values; if exactly one distinct color turns up (true for most simple single-color brand marks), use it directly; (2) otherwise (raster image — PNG etc. — or an SVG with zero/multiple distinct fills), draw the image onto a small offscreen canvas and run `saturationWeightedAverage()` — each opaque pixel's contribution is weighted by its HSL saturation squared, so a small vivid foreground glyph dominates the result over a large flat dark/muted background tile (common for app-icon-style PNGs: a colorful mark centered on a big dark rounded-square backdrop). A plain unweighted average would instead mostly just describe the backdrop, producing a muddy, barely-noticeable color close to the theme's own `--color-surface`. If the weighted pass finds no meaningful color signal at all (weight sum near zero — a genuinely grayscale/monochrome icon, e.g. solid black or white), it falls back to `plainAverage()` so those icons still get *some* representative shade instead of no tint at all. Existing custom-icon items uploaded before this feature (or before this saturation-weighting revision) won't have a tint, or may have the old muddier one, until their icon is re-uploaded — an accepted gap, not specially handled.

**Page background**: `body` in `src/index.css` layers two static `background-image` gradients over `--color-bg` — a `radial-gradient` vignette (darkens toward the edges/corners, transparent in the readable center) and a `repeating-linear-gradient` scanline texture (faint 1px-on/2px-off horizontal lines) — plus `background-attachment: fixed`. Both are static (no `@keyframes`), so there's nothing to gate behind `prefers-reduced-motion`. Since every card/panel (`FetchHeader`, `ItemCard`, `ItemDetail`, admin panels) paints its own opaque-ish background on top, this texture is only visible in the page's negative space around them, not layered over content.

**File input styling**: native `<input type="file">` buttons are unstyled/tiny by default and easy to miss. `ItemForm`'s custom-icon upload input uses Tailwind's `file:` variant (targets `::file-selector-button` directly, no hidden-input/label trick needed) to give the browse button the same bordered/accent-colored look as the rest of the form's buttons.

**Page-load fade-in** (`src/layouts/SiteLayout.tsx`, `src/lib/motionVariants.ts`): the outer `<motion.main>` and each page's top-level sections share a parent/child `variants` pair (`containerVariants`/`sectionVariants`) — Framer Motion automatically propagates the parent's `staggerChildren`/`delayChildren` timing to children using the same variant names (through React context, not DOM parentage, so this still works across the `SiteLayout` → `<Outlet/>` → page boundary), so each section fades and slides in ~120ms after the previous one with no manual per-section delay math. The whole tree is wrapped in `<MotionConfig reducedMotion="user">` (from `motion/react`), which automatically drops the `y` slide for users with `prefers-reduced-motion` set while still letting the opacity fade play — the same respect-the-preference approach already used for the `cursor-blink`/`terminal-cursor` animations, just via Motion's built-in mechanism instead of a manual CSS media query.

**Boot sequence** (`src/components/BootSequence.tsx`): a purely decorative simulated Linux kernel/systemd boot log that plays before `<motion.main>` on first load — a fixed list of `dmesg`/`[  OK  ]`-style lines revealed one at a time via a `setTimeout` chain (same tick-based pattern as `useTypewriter`, but whole-line reveal rather than character-by-character, matching how real boot logs actually print). `SiteLayout.tsx` toggles between `<BootSequence>` and `<motion.main>` inside an outer `<AnimatePresence mode="wait">` (nested around the software-stack page's own `ItemDetail` `AnimatePresence`, which is unrelated and unaffected) so the boot overlay fully fades out before the main content's own entrance begins, rather than the two overlapping. Plays once per browser **session**, gating entry to *any* public page rather than being tied to one specific page (`sessionStorage`, key `thrax-site:booted` — checked directly in `useState`'s initializer, no `useEffect`/no SSR guard, consistent with how `useUrlSyncedFilters` already reads `window.location` directly), is click-to-skip, and — checked manually via `window.matchMedia('(prefers-reduced-motion: reduce)')` inside the component rather than relying on `MotionConfig` alone, since skipping the sequence *entirely* (not just softening it) is the correct behavior here — is bypassed altogether under that preference.

Motion: a blinking text-cursor (`_`) appears after an item name on card hover/focus. Implemented as a plain CSS rule scoped to `.group:hover .cursor-blink` / `.group:focus-visible .cursor-blink` (**not** an unconditional `.cursor-blink { animation: ... }`) — the animation itself must be conditional on the hover/focus selector, or its keyframe-driven opacity would override the `opacity-0`/`group-hover:opacity-100` show/hide utilities and blink constantly regardless of hover state. Disabled under `@media (prefers-reduced-motion: reduce)` using the same selector (so specificity matches and the override actually wins). A second, unconditional variant, `.terminal-cursor` (same `@keyframes cursor-blink`, always animating), is used for the standalone `|` cursor at the end of every terminal-window header's Shell: line, and for the name cursor in `ItemDetail` (continuous there instead of hover-gated, since the detail view is already the active/open state).

**Scrollbar**: a global rule in `index.css` sets `scrollbar-color`/`scrollbar-width` (Firefox) plus `::-webkit-scrollbar*` pseudo-elements (Chromium/Safari) so the scrollbar thumb uses `--color-accent` (brightening to `--color-accent-2` on hover) against a `--color-bg` track, instead of the browser default.

**No-results state** (`SoftwareStackPage.tsx`): when `visibleItems` is empty post-filter/search, shows a `❯`-prefixed message instead of an empty grid — distinguishing "no tools added yet" (`items.length === 0`, nothing to clear) from "no matches" (search/filters excluded everything), and in the latter case offering an inline "clear filters" action that resets both `searchQuery` and `selected` at once.

Every terminal-window header's Shell: line runs through `src/hooks/useTypewriter.ts` — a small state machine (tracked via refs, not just React state, to survive being re-triggered mid-animation) that deletes whatever's currently displayed down to empty, then types the new target string out character by character, re-running every time that target string changes (its effect is keyed on `[target]`). On first mount, since nothing's displayed yet, it skips straight to typing. This is a deliberate full clear-and-retype on every change (not a common-prefix diff), matching the terminal-redraw feel intentionally over a smarter/smoother diff. Most headers pass a static target (`WhoamiHeader`'s `whoami`, `CvHeader`'s `--cv`, `ProjectsHeader`'s `--projects`, `BlogHeader`'s `--blog`, typed once on mount and never again); two are dynamic — `FetchHeader`'s `Shell:` retypes when the filter selection changes (the target is the joined shell-flag string), and `HardwareHeader`'s retypes when the selected device changes (the target is `--{selectedDeviceId}`), and `BlogPostHeader`'s target (`--post={post.id}`) differs per post but doesn't itself change post-mount since the component remounts on route change anyway.

### Data model

```ts
// src/types/item.ts
interface TechItem {
  id: string;                 // slug, e.g. "proton-vpn"
  name: string;
  tags: string[];              // free-form tag ids, stored in Postgres as text[]
  icon: IconRef;
  description?: string;
  url?: string;
  category?: string;           // id of a Category (Supabase `categories` table), not free text — see "Category grouping" below
  installCommands: InstallCommand[]; // package-manager commands, stored as jsonb; [] not undefined, same convention as tags
}

interface InstallCommand { manager: string; command: string } // e.g. { manager: "brew", command: "brew install --cask protonvpn" }

type IconRef =
  | { kind: "simple-icons"; slug: string }   // resolved from the offline-bundled set
  | { kind: "custom"; url: string; tint?: string }; // uploaded to Supabase Storage; tint extracted at upload time, see below

// src/types/filter.ts
interface FilterTag { id: string; label: string; group: string }   // Supabase `tags` table
interface FilterGroup { id: string; label: string; order: number } // src/data/filterTags.ts, static

// src/types/category.ts
interface Category { id: string; label: string } // Supabase `categories` table

// src/types/post.ts
interface Post {
  id: string;          // slug, e.g. "setting-up-cachyos"
  title: string;
  excerpt?: string;
  body: string;         // markdown
  publishedAt?: string; // undefined/null means draft
} // Supabase `posts` table

// src/types/github.ts
interface GithubRepo { id: number; name: string; description?: string; url: string; language?: string; stars: number; updatedAt: string }
// mapped from the live GitHub API response in src/lib/github.ts, not persisted anywhere

// src/types/device.ts
interface DeviceSpec { label: string; value: string } // e.g. { label: "CPU", value: "Ryzen 9 7950X" }
interface ModelCredit { creator: string; sourceUrl: string; license?: string } // credits the Sketchfab author
interface Device {
  id: string;        // slug, e.g. "desktop-pc"
  name: string;
  specs: DeviceSpec[]; // ordered, [] not undefined — same convention as TechItem.installCommands
  modelUrl?: string;   // Supabase Storage URL to the device's .glb, undefined until uploaded
  modelCredit?: ModelCredit;
} // Supabase `devices` table
```

Tag *values* on each item, and the tag *catalog* itself (id/label/group), both live in Supabase — the admin panel can add a new tag on the fly (via `TagPicker`, see below) and it's immediately usable everywhere, no code change needed. Only the *groups* ("Operating System", "Topic", "Featured") stay a small hand-maintained static array in `src/data/filterTags.ts` — adding a new group is a deliberate taxonomy decision, not routine content entry, so it's left as a manual code change (schema migration included, since the `tags.group_id` column has a `check` constraint enumerating valid groups).

**"Recommended" tag** (`RECOMMENDED_TAG_ID` in `filterTags.ts`): a specific, code-recognized tag within the "Featured" group. Unlike ordinary tags, its presence on an item has two extra effects, both driven purely by checking `item.tags.includes(RECOMMENDED_TAG_ID)` — no separate boolean field: `sortRecommendedFirst()` (`lib/filtering.ts`) sorts recommended items to the front of the grid (stable sort, so relative order is otherwise preserved), and `ItemCard` renders a small ★ badge (secondary accent color, top-right corner) on them. Being an ordinary tag under the hood means it also shows up as a normal filterable flag in `FilterBar` (`--recommended`) and in `ItemDetail`'s grouped tag list, for free — no special-casing needed there. The "Featured" group exists specifically so a curation/meta tag like this doesn't get mixed into "Topic," which describes properties of the tool itself, not the site owner's opinion of it.

**Category grouping** (`groupByCategory()` in `lib/filtering.ts`, `CategorySection.tsx`): once the item list gets large, a flat grid gets cluttered, so `SoftwareStackPage.tsx` groups `visibleItems` by `item.category` into labeled sections (`❯ BROWSER`, `❯ GAMING`, ...) — each just a heading followed by the *same* `ItemGrid` component, so nothing about card rendering, the shared-`layoutId` detail-view morph, or `sortRecommendedFirst` changes; recommended items still sort first, just *within* their own category section rather than being pulled into a separate cross-cutting one (deliberately — pulling them out would make a category look like it's missing something). `item.category` holds a **category id**, resolved to a display label via the `categories` catalog (`useCategories()`, passed into `groupByCategory(items, categories)`) — categories are created once via the admin panel's `CategoryPicker` (single-select sibling of `TagPicker`, see "Admin panel" below) and picked from existing ones thereafter, the same click-to-reuse workflow as tags, which is why case-drift ("Browser" vs "browser") is no longer a concern the grouping logic has to paper over. Categories deliberately live in their own `categories` table rather than being folded into `tags`/`FilterGroup` — a tag group is multi-select and automatically becomes a public filter facet (every group is iterated generically in `FilterBar`), whereas a category is single-select-per-item and intentionally stays out of the public filter UI (grouping/display only); a separate table avoids needing to special-case or exclude a "Category" group from that generic iteration. Categories sort alphabetically by label; uncategorized items — or an item whose `category` id no longer resolves in the catalog (e.g. a stale reference) — land in an "Other" bucket always shown last. If literally nothing has a category set yet, `SoftwareStackPage.tsx` falls back to today's flat, headerless grid instead of showing a single pointless "❯ OTHER" heading — grouping only kicks in once it's actually being used.

### Supabase layer

- **`items` table**: `id`, `name`, `tags text[]`, `description`, `url`, `category` (a `categories.id`, not free text), `icon_kind`, `icon_value` (slug or Storage URL), `icon_tint` (nullable — extracted color for custom icons only, see "Per-item tint" below), `created_at`.
- **`tags` table**: `id`, `label`, `group_id` (`'os' | 'topic'`, checked against the static groups), `created_at`. No update/rename policy (tags are only ever added or deleted, never renamed) — see "Deleting tags" below.
- **`categories` table**: `id`, `label`, `created_at`. Same never-renamed, only-added-or-deleted convention as `tags`, and same admin-only write RLS pattern; unlike `tags` it has no `group_id` (categories aren't grouped) and its rows are never iterated by `FilterBar`. `supabase/schema.sql` includes a one-time backfill that converts any pre-existing free-text `items.category` values into real catalog rows (slugified id, original text as label) and repoints `items.category` at the new ids — safe to re-run.
- **`posts` table**: `id` (slug pk), `title`, `excerpt` (nullable), `body` (markdown text, may embed `![]()` images and raw `<video>` tags — see "Blog images/video" above), `published_at` (nullable timestamptz — null means draft), `created_at`. Unlike `items`/`tags`/`categories`, its public `select` policy is conditional (`published_at is not null or auth.uid() = '<admin-user-id>'`) rather than unconditionally public, so the admin can read/edit drafts through the same `usePosts()`/`fetchPosts()` path the public blog list uses.
- **`pinned_repos` table**: `id` (a `"owner/repo"` string, pk), `created_at`. No display data stored — just which repos to additionally live-fetch from GitHub for the Projects page (see "Pinned (contributed) repos" above). Same add-or-delete-only convention as `tags`/`categories` (no `update` policy).
- **`devices` table**: `id`, `name`, `specs jsonb` (ordered `{label, value}` list), `model_url` (nullable, an admin-uploaded `.glb`'s public Storage URL), `model_credit` (nullable jsonb `{creator, sourceUrl, license?}`), `created_at`. Unlike `tags`/`categories`/`pinned_repos`, it gets a real `update` policy like `items`/`posts` — specs/models are expected to be edited in place (e.g. a RAM upgrade or swapping in a better model) rather than deleted and re-added.
- **`timeline_entries` table**: `id`, `role`, `org`, `start_date` (not null), `end_date` (nullable — null means the role is ongoing, renders as "Present"), `description` (nullable, free text), `position` (integer, admin-controlled via drag-and-drop, not derived from `created_at`/chronology like every other table's ordering), `created_at`. Gets a real `update` policy like `devices`/`posts` — entries and their order are expected to be edited in place.
- **Storage buckets**: `icons` (custom-uploaded icon images for items not covered by `simple-icons`), `post-media` (images/video embedded in blog post bodies), `device-models` (admin-uploaded `.glb` files for the hardware page).
- **Auth**: a single admin account. Public sign-up disabled at the project level; the admin user is created once via the Supabase dashboard.
- **RLS**: public `select` on `items`/`tags`/`categories`/`pinned_repos`/`devices`/`timeline_entries` (anon key, read-only, unconditional); public `select` on `posts` gated to published rows (see above); `insert`/`update`/`delete` on `items`, `posts`, `devices`, and `timeline_entries`, and `insert`/`delete` on `tags`, `categories`, and `pinned_repos`, restricted to `auth.uid() = '<admin-user-id>'`. Same read-public/write-admin-only pattern on the `icons`, `post-media`, and `device-models` buckets.
- **Client**: `src/lib/supabaseClient.ts`, initialized from `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` (Vite env vars, kept in `.env.local`, not committed). The anon key is safe to expose client-side by design — RLS protects writes, not key secrecy.
- The public page fetches items and tags once on load into React state (`useItems`/`useTags`); all filtering happens client-side against that in-memory data (no per-filter-click network calls).

### Filtering algorithm

Pure, framework-independent function in `src/lib/filtering.ts`:

```
matches(item, selectedTagsByGroup) =
  every group g:
    selectedTagsByGroup[g] is empty
    OR item.tags intersects selectedTagsByGroup[g]
```

Filter state is `Record<groupId, Set<tagId>>` synced to `URLSearchParams` via `src/hooks/useUrlSyncedFilters.ts` — a drop-in `useState` replacement (same tuple shape) that reads the initial selection from `window.location.search` on mount and mirrors changes back via `history.replaceState` (no `popstate` listener; back/forward filter-history navigation isn't a goal, only shareable/bookmarkable links).

**Free-text search** (`SearchBox.tsx`, `matchesSearch`/`searchItems` in `filtering.ts`): a separate, simpler mechanism from tag faceting — plain case-insensitive substring match on `item.name` only (not description/tags), deliberately not URL-synced (`SoftwareStackPage.tsx` holds `searchQuery` in plain `useState`) since shareable search links weren't asked for, unlike the tag filters. Composed in `SoftwareStackPage.tsx` as `filterItems(searchItems(items, searchQuery), selected)` — search narrows first, tag-faceting applies on top, so the two combine with AND semantics. Styled as an inline `❯ ` prompt-prefixed underline input rather than a boxed search field, matching `FilterBar`'s prompt-symbol convention instead of introducing a different visual language for search vs. filter.

### Animation notes

`AnimatePresence` wraps the mapped grid so filtered-out items animate out; the `layoutId={`item-${item.id}`}` on each card (in place of a plain boolean `layout`) drives FLIP-based reflow of the remaining items *and* doubles as the shared-element id for the click-to-expand detail card (see below) — `layoutId` already implies the same local layout-animation behavior `layout` would, so there's no need for both. Every card needs a stable `key={item.id}`. No virtualization needed at the expected scale (dozens to low hundreds of items).

### Item detail card (`src/components/ItemDetail.tsx`)

Clicking an `ItemCard` (now a `motion.button`, so it's natively keyboard-accessible) calls `onSelect(item)`, set from `SoftwareStackPage.tsx`'s `selectedItem` state. `ItemDetail` renders a fixed, centered overlay whose inner card shares the *same* `layoutId={`item-${item.id}`}` as the clicked `ItemCard` — Framer Motion automatically animates the "morph" between the two across the tree, no manual position math and no `LayoutGroup` needed (there's only one grid and one detail overlay, and ids are unique per item). Shows, in order: the item's tags (grouped by category, styled as the same `--{id}` chips used in `FilterBar` — static, non-interactive spans copying that visual treatment rather than reusing `FilterChip` itself, since one is clickable and this isn't), its `description` (only if set), its install commands (only if any — see below), and a "Visit website" link to `item.url` (only if set) opening in a new tab — descriptive info first, then "how to get it," then "learn more." Needs `allTags`/`groups` passed down from `SoftwareStackPage.tsx` (same `tags`/`filterGroups` the public `FilterBar` already uses) purely to resolve each tag id to its label/group for display. Closes via backdrop click, an explicit `×`, or `Escape` (a `keydown` listener in a `useEffect` — a legitimate external-system-sync effect, same reasoning as `Icon.tsx`'s lazy-load effect).

**Install commands** (`src/components/CopyableCommand.tsx`): each entry in `item.installCommands` (free-form `{ manager, command }` pairs — the admin types the *entire* command, not just a package name, since managers need different flags/casks/taps that can't be auto-templated) renders as a `$ {command}` shell line with a copy button (`navigator.clipboard.writeText`, brief local "Copied!" confirmation via a timeout, silently no-ops if the clipboard API throws). Stored as `items.install_commands jsonb` — a flexible per-item list rather than fixed `brew`/`winget`/... columns, since any given item only supports a handful of the many possible managers. The admin-form editor (`ItemForm.tsx`) is a repeatable two-input-per-row list (manager, command) with add/remove, same spirit as `TagPicker`'s pattern; blank rows are dropped and values trimmed on submit.

**"Search on this manager" links** (`src/lib/packageManagerSearch.ts`): next to each install-command row's manager input, a live "search ↗" link opens that manager's own package-search page in a new tab, pre-filled with the item's name — a small static alias→URL-template table (`brew`/`homebrew`, `choco`/`chocolatey`, `winget`, `pacman`/`arch`, `aur`, `apt`/`ubuntu`, `debian`, `snap`, `flatpak`, `npm`, `cargo`, `pip`/`pypi`, `gem`, `scoop`), matched case-insensitively; unrecognized manager names just show no link. Every URL was verified directly (curl with a real browser UA) rather than assumed — notably **Homebrew has no linkable search page at all** (its site's search is a client-side-only Algolia widget with no server route), so its entry points at GitHub code search across the `Homebrew/homebrew-cask` tap instead. This is deliberately *not* live in-app search-and-autofill: public search-API coverage across these registries is too inconsistent (winget has no reliable public API at all) and CORS support unverifiable from outside a real browser, so the admin still copies the exact command back from the opened search page themselves — this only automates the navigation + query-typing step.

### Icon lookup (`src/lib/simpleIcons.ts`)

- Icon **metadata** (title/slug/hex for all ~3,500 `simple-icons` icons) is bundled eagerly via the package's `./icons.json` export (`simple-icons/icons.json`, ~450KB raw) — used for `getSimpleIconMeta(slug)` (color + display name) and `searchSimpleIcons(query)` (the admin form's icon picker).
- Each icon's **SVG markup** is loaded lazily, one file per icon, via `import.meta.glob('../../node_modules/simple-icons/icons/*.svg', { query: '?raw', import: 'default' })` in the same file — this code-splits ~3,459 tiny per-icon chunks so the main bundle doesn't eagerly ship all path data (that would be ~15MB uncompressed). The glob's module-reference table still adds real weight to the main bundle (~180KB gzip) as the cost of supporting "any slug, no redeploy."
- `Icon.tsx` combines both: renders nothing until the lazy SVG chunk resolves (async, via `useEffect` + local state — a legitimate use of an effect since it's synchronizing with an external system, a dynamically imported module), then injects the markup via `dangerouslySetInnerHTML` (safe here: the content is trusted, locally bundled vendor SVG, never derived from arbitrary user input beyond selecting a known slug) recolored via a wrapping `<span style={{ color: '#'+hex }}>` plus `fill="currentColor"` patched into the SVG string.
- `tsconfig.app.json` needs `resolveJsonModule: true` for the `icons.json` import to type-check.

### Admin panel (`src/admin/`)

- Routing: `/admin` is its own top-level `react-router-dom` route in `main.tsx`, a sibling of the `SiteLayout`-wrapped public routes rather than nested under it (see "Site structure" above) — kept a standalone control-panel surface with no public nav/boot sequence.
- `AdminPage.tsx` has an `activeTab` (`'items' | 'posts' | 'projects' | 'hardware' | 'timeline'`) state switching between the items UI (unchanged), the posts UI (`PostList`/`PostForm`, added for the blog), the pinned-repos UI (`PinnedRepoList`, added for contributor repos), the devices UI (`DeviceList`/`DeviceForm`, added for the hardware page), and the CV timeline UI (`TimelineEntryList`/`TimelineEntryForm`, added for the CV page's timeline — see "CV page" above) — the five collections don't interact, so this is a plain tab toggle rather than shared state.
- `TimelineEntryForm.tsx`/`TimelineEntryList.tsx` are a mirror of `DeviceForm.tsx`/`DeviceList.tsx`'s shape (same auto-slug-`id`, same inline-edit-in-place-of-the-row placement), plus a "Currently here" checkbox that clears/disables the end-date input and maps to `endDate: undefined` on submit. `TimelineEntryList.tsx` is additionally the only drag-and-drop-reorderable list in the app: `@dnd-kit`'s `DndContext`/`SortableContext`/`useSortable`, a small grip-handle span (not the whole row) carrying the drag `listeners` so Edit/Delete stay independently clickable, and local `displayOrder` state reconciled from the `entries` prop via `useEffect` so a drag reorders instantly rather than waiting on the persist-then-refetch round trip — the one deliberate exception to this codebase's usual "mutate then refetch, never optimistically patch local state" rule. `handleDragEnd` calls `reorderTimelineEntries` (`src/lib/timeline.ts`) with the new ordered id list.
- `AdminPage.tsx` gates on `useSession()` (`src/hooks/useSession.ts`, wraps `supabase.auth.getSession()` + `onAuthStateChange`): shows `LoginForm` (email/password via `supabase.auth.signInWithPassword`) when signed out, otherwise the item list + form.
- **Add vs. edit form placement**: adding a new item shows `ItemForm` above `ItemList`, in the same spot as the "Add item" button it replaces (there's no existing row to anchor a brand-new item to). Editing an item instead renders the form *inline*, inside `ItemList` in place of that item's row (`ItemList`'s `editingItemId`/`editForm` props — `editForm` is the already-constructed `<ItemForm/>` element built once in `AdminPage`, so `ItemList` doesn't need every individual form prop threaded through it) — this avoids forcing a scroll back to the top of a long list just to see the form you opened. `AdminPage`'s `showForm`/`editingItem` state is unchanged by this (still two independently-set variables, kept in sync at each call site); only where the resulting form renders differs based on whether `editingItem` is set.
- `ItemForm.tsx` handles both add and edit (the `id`/slug field is auto-derived from `name` via `slugify()` until manually edited, and is disabled entirely when editing an existing item since it's the Postgres primary key). Icon selection is a radio toggle between **simple-icons** (text input backed by `searchSimpleIcons` suggestions) and **custom upload** (`<input type="file">`, uploaded via `src/lib/storage.ts`'s `uploadIcon(itemId, file)` to the `icons` Storage bucket at `${itemId}/${timestamp}-${filename}`, then stored as `{ kind: "custom", url: <public URL>, tint }`). A newly-selected custom file also runs through `extractIconTint()` (see "Per-item tint" above) with a small color-swatch preview next to the file input; editing an existing custom-icon item without picking a new file reuses both the existing URL and tint as-is.
- **Description + URL auto-fill**: an "Auto-fill from Wikipedia" button (above the Description/URL fields) calls `fetchWikipediaInfo(name)` (`src/lib/wikipedia.ts`) and fills *both* fields independently from one lookup. It tries an exact Wikipedia REST summary lookup by title first, falls back to the MediaWiki search API to resolve a near-miss title, and prefers the short Wikidata-style `description` field over the longer `extract` paragraph. The summary response also carries a `wikibase_item` (Wikidata QID) for free — when present, a follow-up call to Wikidata's `wbgetclaims` for property **P856** ("official website") supplies the URL, picking the claim with no language qualifier or one tagged English (`Q1860`) since some items (e.g. Proton products) have one P856 value per locale. Coverage isn't universal and the two fields resolve independently (a "not found" message only shows if *both* come back empty); the admin can always edit or ignore the result. This is a one-time, explicit, admin-side convenience call — it does not touch the public page or add any runtime dependency there, consistent with the site staying static/offline-first for visitors.
- `TagPicker.tsx` (used inside `ItemForm`) replaces free-text tag entry: shows the item's currently-selected tags as removable pills, all catalog tags grouped and clickable below (reusing the same grouped-chip visual pattern as the public `FilterBar`) to toggle them on/off, and a "+ New tag" control (label + a 2-way Operating System/Topic choice) that calls `createTag()` (`src/lib/tags.ts`), refetches the shared tag list via `useTags()`, and auto-selects the new tag onto the item being edited.
- **Deleting tags**: each catalog tag in `TagPicker`'s grid has its own small delete control (deliberately distinct from the "×" on the selected-tags pills, which only removes the tag from the current item). `AdminPage.handleDeleteTag` — not `TagPicker` itself — owns the confirm dialog (naming how many items are affected, via a scan of the already-loaded `items`) and the actual cascade: it strips the tag from every affected item (`updateItem`) *before* deleting the tag row (`deleteTag`, `src/lib/tags.ts`) so a tag is never removed from the catalog while items still reference it. It returns a `boolean` (deleted vs. cancelled) specifically so `TagPicker` can tell those apart — only a confirmed deletion also strips the tag from the currently-open item's local selection (covers a not-yet-saved new item, which wouldn't appear in the "affected items" scan).
- `CategoryPicker.tsx` (used inside `ItemForm`) is the single-select sibling of `TagPicker` for `item.category`: shows every catalog category as a clickable chip (clicking the already-selected one clears the selection back to "no category," unlike `TagPicker`'s independent toggles), and a "+ New category" control (label only — no group choice, since categories aren't grouped) that calls `createCategory()` (`src/lib/categories.ts`), refetches via `useCategories()`, and auto-selects the new category onto the item being edited. Its per-chip delete control and `AdminPage.handleDeleteCategory` cascade (confirm → strip `item.category` from affected items via `updateItem` → delete the catalog row → refetch both → return a `boolean`) are a line-for-line mirror of tag deletion above.
- `ItemList.tsx` renders existing items with Edit/Delete actions; delete asks for confirmation via `window.confirm`.
- Mutations go through `src/lib/items.ts` (`createItem`/`updateItem`/`deleteItem`, plus the row↔`TechItem` mapping shared with `useItems`'s `fetchItems`) — RLS on the `items` table is what actually enforces admin-only writes; the client just surfaces whatever error Postgres/RLS returns.
- After any mutation, `AdminPage` calls `useItems()`'s `refetch()` to reload the list rather than optimistically patching local state.
- `PostForm.tsx`/`PostList.tsx` are a line-for-line mirror of `ItemForm.tsx`/`ItemList.tsx`'s shape (same auto-slug-from-title-until-manually-edited `id` field, same inline-edit-in-place-of-the-row placement via `editingPostId`/`editForm` props), simplified to the post schema: title, id, excerpt, a markdown `body` textarea, and a "Published" checkbox that sets/clears `publishedAt` (preserving the original `publishedAt` when re-saving an already-published post, rather than bumping it to "now" on every edit). `PostForm` also has the Image/Video insert-at-cursor controls described in "Blog images/video" above. Mutations go through `src/lib/posts.ts` (`createPost`/`updatePost`/`deletePost`), same pattern as `lib/items.ts`.
- `PinnedRepoList.tsx` is a flat add/delete list (no per-item edit form needed, unlike items/posts — a pinned repo is just a reference, nothing to edit) for the `pinned_repos` table: pasting a URL or `owner/repo` into the add field first calls `fetchGithubRepo` to confirm the repo is real/public, then `createPinnedRepo` (`src/lib/pinnedRepos.ts`) only if that succeeds; each listed entry has its own delete button (`deletePinnedRepo`, plain `window.confirm`, no cascade needed since nothing else references a pinned-repo id).
- `DeviceForm.tsx`/`DeviceList.tsx` are a line-for-line mirror of `ItemForm.tsx`/`ItemList.tsx`'s shape (same auto-slug-from-name-until-manually-edited `id` field, same inline-edit-in-place-of-the-row placement via `editingDeviceId`/`editForm` props): name, a specs repeatable list using the exact add/update/remove-by-index pattern `ItemForm.tsx` already uses for `installCommands` (label/value pair per row, blank rows dropped and values trimmed on submit), a `.glb` file input (`uploadDeviceModel(id, file)` — `src/lib/storage.ts`, same shape as `uploadIcon`/`uploadPostMedia` — only re-uploaded if a new file is picked; editing a device without choosing one keeps its existing `modelUrl`, same as `ItemForm`'s custom-icon re-edit behavior), and three credit text inputs (Creator/Source URL/License) that populate `modelCredit` only when at least Creator or Source URL is filled in. `DeviceList.tsx` shows a `"3d model"`/`"no model"` indicator per row instead of an edit-form field, same spirit as `PostList.tsx`'s published/draft indicator. Mutations go through `src/lib/devices.ts` (`createDevice`/`updateDevice`/`deleteDevice`), same pattern as `lib/items.ts`.

### Deployment implication

The site remains a static SPA build (`vite build`), deployable to any static host; Supabase (items/tags/categories/posts fetch, admin auth/writes, icon storage) and the public GitHub REST API (Projects page) are the external runtime dependencies. This is a deliberate tradeoff versus a fully static/offline site, made specifically to support the admin-panel requirement. With `react-router-dom` now handling every public route (not just `/admin`), the static host's SPA-fallback/rewrite-to-`index.html` config applies site-wide — a direct visit to any route will 404 without it; see "Deployment note" above for the committed `_redirects`/`vercel.json` rewrite rules.

## Toolchain notes

- **Linter is Oxlint, not ESLint.** Config lives in `.oxlintrc.json` (plugins: `react`, `typescript`, `oxc`). Type-aware lint rules are not enabled by default; enabling them requires installing `oxlint-tsgolint` and setting `"options": { "typeAware": true }` in `.oxlintrc.json` (see README for the exact snippet).
- **TypeScript uses project references**, split across three configs:
  - `tsconfig.json` — root, references the other two, has no compiler options itself
  - `tsconfig.app.json` — the app source (`src/`), target `es2023`, bundler module resolution, `noEmit`, strict-ish unused-locals/params checks
  - `tsconfig.node.json` — Vite config file itself (`vite.config.ts`), Node types
  - Run `tsc -b` (as `npm run build` does) rather than a plain `tsc`, so both projects get checked correctly.
  - `tsconfig.app.json` has `verbatimModuleSyntax: true` — type-only imports (`TechItem`, `IconRef`, `FilterTag`, `FilterGroup`, `SelectedTagsByGroup`, `Session`, etc.) must use `import type`, or the build fails.
  - `tsconfig.app.json` also has `resolveJsonModule: true`, added specifically for the `simple-icons/icons.json` metadata import in `src/lib/simpleIcons.ts`.
- React Compiler is intentionally **not** enabled (per README, to avoid dev/build perf impact).
- **`react-router-dom`** handles all client-side routing (see "Site structure" above); **`react-markdown`** + **`remark-gfm`** + **`rehype-raw`** + **`rehype-highlight`** render blog post bodies (`BlogPostPage.tsx`; `rehype-raw` specifically to allow the raw `<video>` tag through, `rehype-highlight` for fenced-code-block syntax highlighting — see "Blog images/video" and "Blog" above; `rehype-highlight`'s default import bundles `lowlight`'s "common" language subset, not all ~190, keeping the addition modest); **`three`** + **`@react-three/fiber`** + **`@react-three/drei`** render the `/hardware` page's `.glb` models (see "Hardware page" above) — installed with `--legacy-peer-deps` since `@react-three/fiber`'s peer range (`react >=19 <19.3`) hadn't caught up to the installed React 19.3 patch release at the time; no runtime incompatibility observed; **`@dnd-kit/core`** + **`@dnd-kit/sortable`** + **`@dnd-kit/utilities`** power the CV timeline's drag-and-drop reordering in `/admin` (see "CV page" above) — no peer dependencies, installed without `--legacy-peer-deps`. These are the only dependency additions since the site was a single page.
- Imported assets (images used via JS import) live in `src/assets/`; only `public/favicon.svg` remains as a URL-referenced static asset (the template's `icons.svg` sprite was removed along with the placeholder markup that used it). `favicon.svg` is now a small hand-drawn `>_` terminal-prompt glyph (plain SVG shapes, not `<text>`, so it doesn't depend on a webfont being available wherever the browser renders favicons) matching the theme tokens directly (`--color-bg`/`--color-accent` hex values inlined, since `var()` custom properties aren't available in a standalone favicon file outside the page's own stylesheet cascade).
- **Tailwind CSS v4** is wired via the `@tailwindcss/vite` plugin in `vite.config.ts` — CSS-first, no `tailwind.config.js`. `src/index.css` holds the `@theme` design-token block, the base `body` colors, and the `cursor-blink` keyframes/reduced-motion override — see "Visual design" above.
- **Vitest** config lives inline in `vite.config.ts` (a merged `test: {}` block, typed via `/// <reference types="vitest/config" />`), not a separate `vitest.config.ts`. Environment is `jsdom` (needed once component tests were added; pure-function tests run fine under it too, so there's no split-by-file-pattern config) with `setupFiles: ['./src/test/setup.ts']` importing `@testing-library/jest-dom/vitest` (matcher extensions) and calling Testing Library's `cleanup()` in an explicit `afterEach` — `test.globals` stays `false` (this codebase imports `describe`/`it`/`expect` explicitly rather than relying on injected globals, see `filtering.test.ts`), and Testing Library's own auto-cleanup only self-registers when it detects a global `afterEach`, so without this it silently never runs and components leak between tests in the same file. Component tests live next to the component they cover (`Foo.tsx` / `Foo.test.tsx`), not under a separate `__tests__` directory, matching how the pure-logic tests already sit next to their `.ts` files. `@testing-library/user-event`'s `userEvent.setup()` installs its own clipboard stub on `navigator` — a test that overrides `navigator.clipboard` (e.g. `CopyableCommand.test.tsx`) must call `userEvent.setup()` *first*, or its override gets clobbered.
- **Env vars**: custom `VITE_*` vars are typed by augmenting `ImportMetaEnv` in `src/vite-env.d.ts` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_GITHUB_USERNAME`). Real values go in `.env.local` (already covered by `.gitignore`'s `*.local` pattern) — never commit them; `.env.local.example` documents the required keys.
